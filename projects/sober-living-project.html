Sober Living House Management System

A web-based management application designed to organize resident information, financial records, UA compliance, and other day-to-day administrative tasks for a sober living house.

Open Live Demo View Source Code Back to Projects

Project Overview

The Sober Living House Management System is a web-based application designed to centralize common administrative tasks involved in managing a sober living residence.

The application provides a manager dashboard, individual resident records, financial account tracking, weekly rent management, UA compliance tracking, resident archiving, and other tools intended to make day-to-day house information easier to organize and review.

Unlike a project created solely as a programming exercise, this application was designed around a real operational use case. The goal is to identify repetitive or difficult administrative processes and explore how custom software can make those processes more efficient and consistent.

Purpose

Managing a residential program involves keeping track of information that can quickly become scattered across notes, payment records, schedules, and individual resident files.

I created this project to explore how those responsibilities could be brought together into one centralized application where important information can be viewed, updated, and calculated automatically.

The project also gives me an opportunity to build software around evolving real-world requirements. As new administrative needs are identified, the application can be expanded to address them.

Manager Dashboard

The main dashboard provides an overview of current house information without requiring the manager to review every resident individually.

Dashboard information currently includes active resident counts, outstanding balances, resident credits, UA actions requiring attention, and open incident counts.

These values are calculated from the application's resident, transaction, and compliance records and update as the underlying information changes.

Resident Financial Management

Each resident has an individual account history containing rent charges and payments. Rather than storing a balance as a single manually updated number, the application calculates the resident's current balance from their transaction history.

Payments can be recorded with the actual date on which they were received and can include different payment methods. Rent charges can also be assigned to specific billing dates.

The system distinguishes between outstanding balances and resident credits, allowing the dashboard to separately show money owed to the house and money residents have paid in advance.

UA Compliance Management

The application includes a scheduling and record system for resident UA compliance.

A manager can establish a resident's next UA date, view upcoming or unresolved UA activity, document the action taken, and record the result when applicable.

Once a schedule has been established, the application can generate recurring UA records at 14-day intervals. Unresolved records are reflected on the dashboard so that required actions are less likely to be overlooked.

Resident Records and Archiving

Resident records can move through different stages without losing their historical information. Residents who are no longer active can be archived rather than permanently removed from the system.

Archived residents retain their existing financial information and can later be restored to active status if necessary.

The application also includes a safeguard that prevents a resident with existing transaction history from being permanently deleted. In that situation, the manager is directed to archive the resident instead, helping preserve financial history.

Development Process

The application is currently built using HTML, CSS, and JavaScript.

HTML defines the management interface and forms, CSS controls the visual layout and responsive presentation, and JavaScript manages application state, resident records, transactions, balance calculations, UA scheduling, data persistence, and dynamic interface updates.

The current development version uses browser local storage to persist application data between page loads. This allows the core workflows and data model to be developed and tested before introducing a production backend and database.

Challenges and Solutions

Maintaining accurate financial history

One challenge was ensuring that account balances remain connected to the underlying transaction history rather than relying on a manually edited balance.

The application calculates balances from recorded charges and payments, making the transaction ledger the source of the resident's financial position.

Preventing duplicate rent charges

Weekly rent posting requires safeguards so that accidentally running the process more than once does not repeatedly charge the same resident for the same billing date.

Before creating a weekly charge, the application checks the existing transaction history for a matching resident, charge category, and billing date.

Preserving historical records

Permanently deleting a former resident could also remove the context surrounding their financial history.

To address this, the application supports archiving and restoration and prevents permanent deletion when account history already exists.

Managing recurring UA schedules

Compliance tracking requires more than displaying a single status. The application needs to maintain scheduled dates, unresolved records, completed actions, results, and future due dates.

I implemented separate UA records and scheduling logic so that historical activity can be preserved while future due dates continue to be generated.

What I Learned

This project has strengthened my understanding of JavaScript application architecture, DOM manipulation, event handling, state management, data modeling, financial calculations, form handling, validation, date-based logic, and browser data persistence.

It has also given me experience translating real-world requirements into software features. Instead of beginning with a fixed list of programming requirements, the application evolves as actual workflow problems and edge cases are identified.

That process has required me to think not only about whether a feature works, but also about data integrity, historical records, usability, and how one change can affect other parts of the system.

Current Development Status

This project is actively in development and should currently be considered a functional prototype rather than a production resident-management system.

The current version stores information using browser local storage and does not yet include a secure backend, production database, authentication, encryption, or role-based access controls.

Because of these limitations, the public demonstration uses fictional or demonstration resident information and is not intended to store confidential real-world resident data.
